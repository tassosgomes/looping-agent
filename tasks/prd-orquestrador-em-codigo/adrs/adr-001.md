# ADR-001: Orquestrador em TypeScript + Node.js, distribuído via npm

## Status

Accepted

## Data

2026-04-26

## Contexto

O PRD declara o orquestrador como código (RF-03) e adota ACP (Agent Client Protocol) como
único transporte para sub-agentes. Precisamos escolher uma stack que: (a) tenha cliente ACP
maduro, (b) permita hospedar um servidor MCP local para entregar os tools `report_*`
(ADR-002), (c) seja distribuível como CLI single-command, (d) ofereça onboarding razoável
para devs do ecossistema de IA.

Linguagem alvo é decisão da TechSpec conforme nota explícita do PRD.

## Decisão

Implementar o orquestrador em **TypeScript** rodando em **Node.js ≥ 20**, distribuído como
**pacote npm global** (`@looping-agent/cli`).

Cliente ACP: `@zed-industries/agent-client-protocol` (TS oficial mantido por Zed). Servidor
MCP local: `@modelcontextprotocol/sdk` (TS oficial). Empacotamento e tipos compartilhados
entre orquestrador e schemas dos `report_*` ficam no mesmo monorepo.

## Alternativas Consideradas

### Alternativa 1: Python

- **Descrição:** Orquestrador em Python 3.12+, distribuído via pipx/uv.
- **Prós:** MCP Python SDK é primeira-classe; comunidade de IA é Python-friendly.
- **Contras:** Cliente ACP em Python é menos maduro; ecossistema async é fragmentado
  (asyncio vs trio); empacotamento de CLI multi-plataforma exige uv/pipx, ambos com
  fricção de adoção.
- **Por que rejeitada:** Cliente ACP TS é a referência atual. Trocar cliente ACP é o
  trade-off mais alto desta decisão; Python perde aqui.

### Alternativa 2: Go

- **Descrição:** Orquestrador em Go, distribuído como single binary cross-platform.
- **Prós:** Single binary trivial; performance e startup excelentes; concorrência nativa
  via goroutines (útil para futuras paralelizações).
- **Contras:** Cliente ACP em Go provavelmente exige wrapper sobre o protocolo bruto
  JSON-RPC; MCP server em Go também exige re-implementação. Boilerplate mais alto para
  iterar rápido em MVP.
- **Por que rejeitada:** Custo de manter cliente ACP e MCP server caseiros não compensa
  no MVP. Reavaliar para v2 se o produto evoluir para uso em CI/CD massivo.

### Alternativa 3: Rust

- **Descrição:** Orquestrador em Rust, single binary, usando o cliente ACP de referência
  do Zed.
- **Prós:** Performance máxima; cliente ACP de referência é Rust; safety estática.
- **Contras:** Curva de aprendizado e velocidade de iteração mais lentas; comunidade de
  devs alvo (TS/Python) menos confortável para contribuir.
- **Por que rejeitada:** MVP precisa de iteração rápida. Rust é overkill para um CLI
  one-shot local.

### Alternativa 4: Binário standalone (pkg/bun build) sobre TypeScript

- **Descrição:** Mesma stack TS, mas empacotada como binário único via `pkg` ou
  `bun build --compile`.
- **Prós:** Não exige Node.js instalado.
- **Contras:** Binário ~50MB; update manual; menor descoberta no shell.
- **Por que rejeitada:** Custo de operação maior que o ganho. Devs do ecossistema de IA
  já têm Node. Pode virar uma flag de release futura sem bloquear MVP.

## Consequências

### Positivas

- Cliente ACP e MCP SDK ambos primeira-classe em TS — ambos são SDKs oficiais do
  ecossistema, sem necessidade de manter wrapper.
- `npm install -g` e `npm update` fornecem o ciclo de vida do produto sem código novo.
- Tipos TypeScript compartilhados entre schemas dos `report_*`, telemetria e orquestrador
  reduzem bugs de integração.
- Onboarding alinhado com o público-alvo (devs que já usam Claude Code / Codex CLI).

### Negativas

- Requer Node.js ≥ 20 instalado na máquina do dev — assume-se aceitável dado o público
  alvo, mas é uma dependência externa não-trivial.
- Startup do Node tem overhead vs. binário compilado (~100-300ms) — irrelevante para um
  CLI que executa loops de minutos.
- TS strict + ESM exige cuidado com imports e tooling.

### Riscos

- **Risco:** Cliente ACP TS é maduro hoje, mas o protocolo está em evolução e quebras de
  major podem acontecer. *Mitigação:* pin de versão (ADR sobre vamos pinar 1.x); changelog
  monitorado; testes de integração automatizados contra os runtimes alvo.
- **Risco:** Devs sem Node ≥ 20 instalado quebram no setup. *Mitigação:* RF-01 valida
  versão e mensagem de erro acionável aponta como instalar (nvm/volta/asdf).

## Notas de Implementação

- Estrutura sugerida: monorepo com workspaces npm (`packages/cli`, `packages/mcp-server`,
  `packages/schemas`, `packages/telemetry`).
- Build via `tsc` ou `tsup` para output ESM + types.
- Lint: ESLint + typescript-eslint strict.
- Testes: Vitest (unit + integração).
- Versão mínima Node: 20 LTS.
- Empacotamento: `package.json` declara `bin: { "looping-agent": "./dist/cli.js" }`.

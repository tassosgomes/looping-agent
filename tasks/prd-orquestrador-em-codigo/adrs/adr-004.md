# ADR-004: Skills instaladas no escopo do projeto, com update via overwrite + .bak

## Status

Accepted

## Data

2026-04-26

## Contexto

O PRD declara como aberta a decisão de onde instalar as 19 skills `flow-*`: globalmente em
`~/.claude/skills/` (compartilhadas entre projetos) ou no escopo do projeto
(`<projeto>/.claude/skills/`). Decisão impacta UX do setup (RF-01) e política de atualização
(RF-02).

Também é decisão da TechSpec o mecanismo de atualização preservando customizações do
usuário (RF-02 critério: "atualizadas no agente alvo, preservando customizações do usuário
quando documentadas").

## Decisão

**Localização:** instalar as 19 skills em `<projeto>/.claude/skills/` (escopo do projeto).
O setup também cria a estrutura de tasks (`tasks/`) e telemetria (criada lazy).

**Atualização:** comando `looping-agent update` faz **overwrite das skills com backup
automático em `.bak`**:

1. Para cada skill em `<projeto>/.claude/skills/flow-*/SKILL.md`:
   - Calcula hash do arquivo atual.
   - Compara com hash da versão "original" registrada em
     `<projeto>/.claude/.looping-agent-state.json`.
   - Se igual → overwrite limpo, atualiza hash registrado.
   - Se diferente → cria `.bak` antes de overwrite, reporta ao dev "skill X tinha
     customizações; backup salvo em .bak; revise manualmente".
2. Setup também atualiza `.looping-agent-state.json` com a versão do produto e os hashes
   originais das skills da nova versão.

## Alternativas Consideradas

### Alternativa 1: Skills globais em `~/.claude/skills/`

- **Descrição:** Instalar todas as skills uma vez por máquina, compartilhar entre projetos.
- **Prós:** Update único afeta todos os projetos; menos arquivos no repo do dev.
- **Contras:** Customização por projeto exige mecanismo extra; equipes em projetos
  diferentes não podem ter versões diferentes; entra em conflito com a abordagem do
  projeto de versionar skills no repo (decisão expressa pelo dev).
- **Por que rejeitada:** Decisão explícita do dev na fase de discovery: skills devem
  viajar com o repo para que cada projeto possa ter sua versão snapshot.

### Alternativa 2: Híbrido (globais por padrão, override por projeto)

- **Descrição:** Skills vivem em `~/.claude/skills/`. Se `<projeto>/.claude/skills/<nome>/`
  existir, ele tem precedência.
- **Prós:** Default global + escape hatch local.
- **Contras:** Resolver de skills precisa lidar com 2 caminhos; setup precisa explicar 2
  caminhos; debugging "qual versão está rodando?" fica ambíguo.
- **Por que rejeitada:** Complexidade não justificada no MVP. Pode virar uma feature
  opcional via flag em iteração futura.

### Alternativa 3: Update com marker `custom: true` no frontmatter

- **Descrição:** Skill com `custom: true` no frontmatter é ignorada pelo `update`.
- **Prós:** Dev declara explicitamente customizações; nenhum overwrite acidental.
- **Contras:** Dev pode esquecer de remover o marker e ficar para sempre numa versão
  velha; skill customizada pode divergir silenciosamente do contrato esperado pelo
  orquestrador (ex: novo `completion_tool`); confusão sobre o que `custom: true`
  realmente significa.
- **Por que rejeitada:** Marker em frontmatter não escala bem para evolução do produto.
  Backup `.bak` é mais explícito (arquivo presente no FS) e força revisão manual.

### Alternativa 4: 3-way merge usando `.orig` + arquivo atual + nova versão

- **Descrição:** Update detecta mudanças locais e tenta merge automatico (git-like).
- **Prós:** Mantém customizações + atualiza partes não tocadas.
- **Contras:** Conflitos exigem resolução manual; merge automático pode produzir
  arquivos com semântica quebrada; complexidade alta de implementação e de UX.
- **Por que rejeitada:** Skills são ~300-500 linhas de Markdown — overhead de merge
  não compensa. `.bak` + revisão manual é mais transparente.

## Consequências

### Positivas

- **Skills versionadas com o projeto:** time pode commitar skills, revisar diffs em PRs,
  e congelar uma versão por release.
- **Customização trivial:** dev edita o markdown direto, comita junto com o código.
- **Update reversível:** `.bak` permite rollback sem rodar comando.
- **Sem complexidade de resolver path:** setup e orquestrador olham um único caminho
  (`<projeto>/.claude/skills/`).

### Negativas

- **19 markdowns no repo de cada projeto:** ~150KB de overhead. Mitigação: time pode
  optar por `.gitignore` se preferir tratar como dependência externa (com setup de novo
  ao clonar).
- **Atualizar N projetos exige rodar `update` em cada um:** ferramenta auxiliar
  (`looping-agent update --all-projects ~/repos/*`) pode ser adicionada se virar dor.
- **Customizações exigem revisão manual a cada update:** dev vê o `.bak`, copia ajustes,
  apaga. Aceitável no MVP; alternativa de merge é Phase 2+.

### Riscos

- **Risco:** Dev customiza uma skill de fase (ex: `flow-implementer`) de forma que
  quebra o contrato com o orquestrador (ex: muda `completion_tool` no frontmatter).
  *Mitigação:* validador no setup/update verifica frontmatter canônico das skills de
  fase contra schema esperado (ADR-005 cobre o fail-fast no setup).
- **Risco:** Dev não rebaixa o `.bak` e fica acumulando lixo. *Mitigação:* `update`
  imprime aviso "skill X tem .bak desde [data]; revise"; `looping-agent doctor` lista
  pendências.

## Notas de Implementação

- `<projeto>/.claude/.looping-agent-state.json` esquema:
  ```json
  {
    "looping_agent_version": "1.0.0",
    "installed_at": "2026-04-26T13:00:00Z",
    "skills": {
      "flow-prd-creator": { "hash": "sha256:...", "installed_version": "1.0.0" },
      ...
    }
  }
  ```
- Hash calculado após normalização (LF line endings, trim trailing whitespace) para
  evitar falsos positivos de "modified".
- `setup` é idempotente: se uma skill já existe com hash batendo, não toca.
- `update` é separado de `setup` — setup só cria, update só atualiza, ambos respeitam
  `.bak`.

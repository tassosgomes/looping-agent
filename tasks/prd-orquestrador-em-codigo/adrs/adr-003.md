# ADR-003: Telemetria como JSON por task no diretório do PRD

## Status

Accepted

## Data

2026-04-26

## Contexto

O PRD (RF-06) exige persistência automática de telemetria estruturada por task, capturando
dados das notificações ACP (`session/update`, `session/prompt`) e dos tool_calls de
conclusão. Métricas a registrar (mínimo): iterações por fase, status final, tokens
input/output por sessão, duração, `stopReason`, contagem de notificações `tool_call`,
issues do reviewer.

Decisões da TechSpec (declaradas como abertas no PRD): formato exato de persistência (JSON,
SQLite, etc.) e localização (diretório do PRD vs diretório global de observabilidade).

## Decisão

Persistir telemetria como **um arquivo JSON por task** localizado em
`tasks/prd-[slug]/telemetry/[N]_telemetry.json`, junto ao PRD.

Schema validado por Zod, tipo compartilhado entre orquestrador e schemas (`packages/schemas/src/telemetry.ts`).

Estrutura por arquivo:

```json
{
  "task_id": 3,
  "prd_slug": "orquestrador-em-codigo",
  "started_at": "2026-04-26T13:00:00Z",
  "ended_at": "2026-04-26T13:14:32Z",
  "duration_ms": 872000,
  "status": "completed | failed | halted",
  "halt_reason": null,
  "phases": [
    {
      "name": "implementer",
      "attempts": [
        {
          "attempt": 1,
          "started_at": "...",
          "ended_at": "...",
          "duration_ms": 480000,
          "stop_reason": "end_turn",
          "tokens": { "input": 12450, "output": 3200 },
          "tool_call_count": 7,
          "completion_tool_invoked": true,
          "completion_input": { "status": "completed", "files_changed": [...], ... },
          "notifications_log_path": "./[N]_telemetry/implementer-attempt-1-notifications.jsonl"
        }
      ]
    },
    { "name": "reviewer", "attempts": [...] },
    { "name": "finalizer", "attempts": [...] }
  ],
  "summary": {
    "total_iterations": 2,
    "total_tokens": { "input": 28900, "output": 7800 },
    "tokens_unavailable": false,
    "review_issues": [...]
  }
}
```

Notificações ACP completas (sequência de `session/update`) ficam em arquivos JSONL
auxiliares dentro de `tasks/prd-[slug]/telemetry/[N]_telemetry/` para preservar trace
completo sem inflar o JSON principal.

## Alternativas Consideradas

### Alternativa 1: SQLite único agregado em `~/.looping-agent/telemetry.db`

- **Descrição:** Um banco SQLite global agregando todas as execuções de todos os PRDs.
- **Prós:** Análise agregada cross-PRD trivial via SQL (média de tokens por PRD,
  distribuição de `stopReason`, etc.); compactação automática; índices.
- **Contras:** Binário, não versionável no git; CI/CD futura precisa montar o BD; menor
  inspeção humana direta; lock contention se 2 execuções rodarem em paralelo
  (improvável no MVP, mas relevante).
- **Por que rejeitada:** O MVP é estritamente local e single-execution. O ganho
  agregado não compensa perder versionamento + diff humano. SQLite pode ser uma
  agregação opcional gerada por `looping-agent telemetry export` em iteração futura.

### Alternativa 2: JSONL append-only por execução

- **Descrição:** `tasks/prd-X/telemetry/run-YYYY-MM-DD.jsonl`, 1 linha por notificação ACP.
- **Prós:** Streaming durante execução (tail -f), análise via jq.
- **Contras:** Formato não-tabular; agregação por task exige scan; arquivo cresce muito
  para tasks longas; difícil correlacionar execuções múltiplas da mesma task.
- **Por que rejeitada:** RF-06 exige "1 arquivo por task com cobertura 100% dos campos
  definidos" — JSONL agregado por execução não bate diretamente com esse critério.
  JSONL fica como auxiliar (notificações brutas) dentro do nosso esquema.

### Alternativa 3: Telemetria global em `~/.looping-agent/telemetry/`

- **Descrição:** Mesma estrutura JSON por task, mas localização global.
- **Prós:** Análise cross-PRD não exige scan de múltiplos repos.
- **Contras:** Telemetria não viaja com o repo; reproduzir bug exige entregar 2
  diretórios (repo + ~/.looping-agent); permissão por usuário; cleanup manual.
- **Por que rejeitada:** Ferramentas de análise cross-PRD podem ler do path canônico
  `tasks/prd-*/telemetry/` em qualquer repo. Manter telemetria junto ao PRD preserva
  reprodutibilidade e auditoria.

## Consequências

### Positivas

- **Versionamento natural:** telemetria viaja com o repo do projeto; PRs do dev podem
  incluir/excluir telemetria conforme política do time.
- **Diff humano possível:** comparar duas execuções da mesma task é `diff` nativo.
- **Reprodutibilidade:** todo o estado para investigar uma falha está dentro do
  diretório do PRD (junto com `tasks.md`, memória, review files).
- **Critério RF-06 cumprido:** "1 arquivo por task com cobertura 100% dos campos
  definidos" mapeia 1:1 com `[N]_telemetry.json`.
- **Tokens opcionais tratados:** runtime que não reporta tokens preenche
  `"tokens_unavailable": true` por sessão, sem quebrar o schema.

### Negativas

- **Análise agregada cross-PRD exige scan:** ferramenta auxiliar ou script para
  varrer `tasks/prd-*/telemetry/` se quiser dashboards globais. Aceitável no MVP.
- **Repo cresce:** se o time não fizer cleanup, telemetria acumula. Mitigação:
  `.gitignore` opcional do diretório `telemetry/` se o time decidir não versionar.
- **Risco de PII em prompts:** notificações ACP podem conter conteúdo sensível.
  Mitigação documentada na seção "Riscos Conhecidos" da TechSpec.

### Riscos

- **Risco:** Tasks que falham em sequências longas geram telemetria grande.
  *Mitigação:* notificações brutas vão para JSONL auxiliar; o JSON principal fica
  resumido. Se alguma task estourar, comprimir o JSONL via gzip on-write é uma
  iteração futura barata.

## Notas de Implementação

- Schema Zod em `packages/schemas/src/telemetry.ts`.
- Writer transacional: telemetria é escrita ao final de cada fase (não no fim de tudo)
  para que halt-on-failure preserve telemetria parcial conforme RF-06.
- Diretório criado lazy quando primeira task começa.
- JSONL auxiliar em `[N]_telemetry/` com 1 arquivo por (fase, tentativa).
- Versão de schema embutida no JSON (`"telemetry_schema_version": "1.0"`) para evolução.

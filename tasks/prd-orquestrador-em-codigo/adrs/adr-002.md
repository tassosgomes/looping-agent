# ADR-002: Servidor MCP local hospedado pelo orquestrador para tools `report_*`

## Status

Accepted

## Data

2026-04-26

## Contexto

O PRD (RF-05) define 3 tools de conclusão (`report_implementer_result`,
`report_review_result`, `report_finalizer_result`) que cada skill de fase deve invocar para
reportar o outcome ao orquestrador. O mecanismo de exposição desses tools ao agent ACP é
decisão da TechSpec.

Restrições:

- Os tools são versionados com o produto (acompanham o orquestrador, não vivem em runtime
  alheio).
- O contrato (schemas) é validado pelo orquestrador no momento de receber a invocação.
- Precisa funcionar em Claude Code, Codex e Copilot CLI sem adapter por runtime.
- O orquestrador roda na mesma máquina que o agent ACP (execução estritamente local).

## Decisão

Implementar um **servidor MCP local hospedado pelo orquestrador**, que sobe junto com cada
execução da Fase B. O servidor declara os 3 tools `report_*` com seus schemas, e o
orquestrador injeta o endereço/handle do servidor na configuração da sessão ACP de cada fase
para que o agent o reconheça como provedor de tools.

Implementação via `@modelcontextprotocol/sdk` (TS), comunicação via stdio entre orquestrador
e MCP server (mesmo modelo de spawn do ACP). MCP server é uma sub-rotina do orquestrador, não
um processo separado de longa duração.

Quando uma skill de fase (ex: `flow-implementer`) executa em uma sessão ACP, o agent vê os 3
tools como disponíveis e os invoca. O orquestrador captura a invocação via notificação ACP
`session/update.tool_call`, valida o input contra o schema interno (Zod), e usa os campos
para decidir o próximo passo do loop.

## Alternativas Consideradas

### Alternativa 1: Tools nativos por runtime ACP

- **Descrição:** Cada runtime (Claude, Codex, Copilot) registra os tools no seu próprio
  modo nativo (ex: Claude `tools` config, Codex `--tool` flag).
- **Prós:** Sem servidor adicional; integração mais "local" ao runtime.
- **Contras:** Multiplica o setup por runtime — cada um tem formato/registro diferente.
  Quebra a premissa de "formato único, sem adapter por runtime" (Visão Geral do PRD).
- **Por que rejeitada:** Mata o principal benefício arquitetural do design "tudo skill".
  Voltar a ter adapter por runtime é regressão.

### Alternativa 2: Tools como skills com convenção de invocação

- **Descrição:** Os tools `report_*` viram pseudo-skills que o agent invoca declarando o
  resultado em formato fixo (ex: bloco JSON em mensagem). Sem MCP.
- **Prós:** Sem servidor MCP; sem dependência adicional.
- **Contras:** Reinventa parsing de stdout — exatamente a alternativa rejeitada no PRD
  (Alternativa 5). Sem schema validation nativa, sem capture estruturada, sem streaming.
- **Por que rejeitada:** Conflita diretamente com a decisão arquitetural do PRD de não
  fazer parsing customizado.

### Alternativa 3: HTTP server local em porta fixa

- **Descrição:** Orquestrador sobe um HTTP server (ex: `localhost:7777`) e os tools
  são invocados via HTTP, expostos ao agent via configuração customizada.
- **Prós:** Mais inspecionável (curl debugging).
- **Contras:** Não é o mecanismo nativo do ecossistema ACP/MCP; conflita com porta
  ocupada; precisa de auth para evitar tools acessíveis por outros processos.
- **Por que rejeitada:** MCP via stdio é o padrão do ecossistema. HTTP adiciona
  superfície de ataque sem ganho real.

## Consequências

### Positivas

- **Formato único entre runtimes:** todo runtime ACP-capable que respeita MCP servers
  reconhece os tools sem adapter.
- **Schema validation nativa:** MCP SDK valida input do tool_call contra schema declarado;
  Zod schemas compartilhados entre orquestrador e MCP server.
- **Streaming preservado:** notificações `session/update.tool_call` chegam em tempo real;
  orquestrador renderiza progresso (RF-03 critério de tempo real) sem hack.
- **Versionamento atrelado ao produto:** schemas evoluem junto com o orquestrador,
  garantia de consistência (RF-05 restrição).

### Negativas

- **Complexidade adicional no setup (RF-01):** o instalador valida que o agent reconhece
  o MCP server local e que stdio funciona. Falha aqui é caso aberto declarado no PRD.
- **Dependência extra (`@modelcontextprotocol/sdk`):** mais uma lib no bundle, mais um
  ponto de evolução para acompanhar.
- **Lifecycle do MCP server:** precisa ser criado/destruído junto com cada execução do
  loop; bug aqui pode deixar processo zumbi.

### Riscos

- **Risco:** Runtime ACP que suporta protocolo mas não respeita MCP server injetado
  (RF-05 questão em aberto: "agent não invoca o tool"). *Mitigação:* RF-04 já cobre
  retry com prompt reforçado (decisão da TechSpec); RF-01 valida disponibilidade dos
  tools no setup.
- **Risco:** MCP SDK breaking changes acompanham ACP em evolução. *Mitigação:* pin de
  versão; testes de integração contra os 2 runtimes alvo a cada release.

## Notas de Implementação

- Pacote do monorepo: `packages/mcp-server`.
- Schemas dos tools: `packages/schemas/src/report-tools.ts` (Zod), exportados para
  consumo no MCP server e na validação do orquestrador.
- Lifecycle: orquestrador faz `spawn` do MCP server no início da execução, conecta
  stdio, e `kill` no shutdown. Per-execução, não daemon.
- Endereço/handle injetado na sessão ACP via parâmetro de configuração nativo do cliente
  ACP (a documentar conforme API atual da `@zed-industries/agent-client-protocol`).
- Captura: orquestrador escuta notificações `session/update`, filtra `tool_call` cujo
  `name` está na allowlist `[report_implementer_result, report_review_result, report_finalizer_result]`,
  valida input via schema, e dispara estado.

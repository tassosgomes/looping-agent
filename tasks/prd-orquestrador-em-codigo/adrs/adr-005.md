# ADR-005: Política de retry para sessões ACP que não invocam o `completion_tool`

## Status

Accepted

## Data

2026-04-26

## Contexto

O PRD (RF-04, RF-05 e Questão em Aberto remanescente) trata o caso em que o LLM dentro de
uma sessão ACP encerra com `stopReason: end_turn` sem invocar o tool_call de conclusão
declarado no `completion_tool` da skill de fase. Isso é violação de contrato e precisa de
uma política de retry específica para evitar loops e garantir progresso.

Decisão da TechSpec: definir mecanismo concreto de detecção e retry.

## Decisão

Implementar **retry com prompt reforçado**, contado dentro do orçamento normal de retries
da fase (limite default 3 conforme decisão de discovery).

Algoritmo na próxima fase:

1. Orquestrador escuta notificações `session/update` durante a sessão ACP.
2. Mantém um flag `completion_tool_seen` (booleano), iniciado como `false`. O nome do tool
   esperado vem do frontmatter `completion_tool` da skill de fase em execução.
3. Quando recebe `session/update.tool_call` com `name === completion_tool`, valida o input
   contra o schema (Zod). Se válido, marca `completion_tool_seen = true` e captura o input.
4. Quando recebe a resposta final de `session/prompt`:
   - Se `stopReason === "end_turn"` E `completion_tool_seen === false`:
     **falha de contrato**. Conta como tentativa, registra na telemetria
     (`stop_reason: "end_turn", completion_tool_invoked: false`), e dispara nova sessão
     ACP com prompt prefixado:

     ```
     [RETRY-CONTRATO] A sessão anterior encerrou sem invocar o tool {completion_tool}.
     Você DEVE invocar {completion_tool} antes de responder com end_turn. Reportar
     resultado parcial é melhor do que não reportar — use status="failed" se houve
     bloqueio, mas SEMPRE invoque o tool.

     <prompt original>
     ```

   - Se `stopReason ∈ {"refusal", "max_tokens", "max_turn_requests"}`: tratado como
     falha de fase normal (RF-04), conta como tentativa, sem prefixo de contrato.

   - Se `stopReason === "end_turn"` E `completion_tool_seen === true`: sucesso de contrato;
     orquestrador prossegue com decisão baseada no input do tool.

5. Esgotado o orçamento de retries (default 3) sem `completion_tool_seen === true`,
   o orquestrador faz halt-on-failure conforme RF-04, persistindo na telemetria:
   - `halt_reason: "contract_violation_completion_tool_missing"`
   - todas as tentativas com `completion_tool_invoked: false`

Não há tratamento "agressivo" diferenciado (1 retry e halt) — o caso é tratado igual a
qualquer outra falha de fase. A diferença é apenas o prompt prefixado.

## Alternativas Consideradas

### Alternativa 1: Halt imediato no primeiro descumprimento

- **Descrição:** Aus\u00eancia do tool é falha de contrato grave; pausa pipeline imediato.
- **Prós:** Conservador, força investigação humana cedo.
- **Contras:** LLMs ocasionalmente esquecem de invocar tools por razões benignas
  (interrupção de contexto, resposta truncada). Halt agressivo gera fricção
  desnecessária. PRD explicitamente desejou retry com prompt reforçado.
- **Por que rejeitada:** Trade-off ruim entre fricção e robustez. Retry simples já
  resolve a maioria dos casos.

### Alternativa 2: Retry com timeout reduzido + halt agressivo após 1 retry

- **Descrição:** 1 retry com prompt reforçado; se falhar de novo, halt sem consumir
  orçamento normal de retries.
- **Prós:** Diferencia "falha de contrato" de "falha de implementação".
- **Contras:** Complica a lógica de retry e a telemetria; LLMs podem ter erros
  consecutivos benignos (sessão muito longa, contexto perdido); orçamento separado
  de retries é prematuro.
- **Por que rejeitada:** Complexidade não compensa. Default de 3 já dá margem.

### Alternativa 3: Auto-injeção do tool_call pelo orquestrador

- **Descrição:** Se a sessão encerra sem o tool, o orquestrador inventa um
  `report_*_result` com defaults conservadores e prossegue.
- **Prós:** Pipeline nunca trava.
- **Contras:** Falsifica resultado; mascara bugs; quebra a premissa do PRD de que
  o tool_call é a "verdade do resultado".
- **Por que rejeitada:** Viola princípio fundamental do RF-05.

## Consequências

### Positivas

- **Recuperação automática para o caso comum** (LLM esquece): retry com prompt
  reforçado resolve sem intervenção humana na maioria das vezes.
- **Halt determinístico** se o problema persiste após 3 tentativas: dev sabe que algo
  estrutural está errado (skill mal escrita? tool não exposto?).
- **Telemetria rastreia o problema:** `completion_tool_invoked: false` por tentativa
  alimenta o ledger e permite identificar runtimes/skills problemáticas.

### Negativas

- **Custo de tokens em LLMs distraídos:** cada retry recarrega o contexto da fase;
  loops longos consomem tokens. Mitigação: telemetria do RF-09 ajuda a quantificar.
- **Não diferencia "esqueceu" de "se recusou":** ambos contam como tentativa. Aceitável
  pelo critério de simplicidade.

### Riscos

- **Risco:** Skill de fase mal escrita instrui o LLM a não invocar o tool. *Mitigação:*
  validador no setup verifica que cada skill de fase declara `completion_tool` no
  frontmatter; texto da skill inclui seção dedicada "Invoque o tool_call ... (obrigatório)".
- **Risco:** MCP server não expõe corretamente o tool, agent recebe lista vazia e nunca
  invoca. *Mitigação:* RF-01 valida disponibilidade dos tools; smoke test no setup
  invoca o MCP server e lista tools.

## Notas de Implementação

- Validação do frontmatter das skills de fase é parte do `setup`/`update`:
  ```typescript
  const phaseFrontmatterSchema = z.object({
    name: z.string().regex(/^flow-(implementer|reviewer|finalizer)$/),
    pipeline_stage: z.enum(["implementer", "reviewer", "finalizer"]),
    consumed_by: z.array(z.literal("orchestrator")),
    completion_tool: z.enum([
      "report_implementer_result",
      "report_review_result",
      "report_finalizer_result",
    ]),
    loads_skills: z.array(z.string().regex(/^flow-/)),
  });
  ```
- Listener de notificações `session/update` mantém estado por sessão (`completion_tool_seen`).
- Ao construir prompt de retry, orquestrador usa um template versionado em
  `packages/cli/src/prompts/retry-contract.ts`.
